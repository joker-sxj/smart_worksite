# 本地大模型评测与验收方法

日期：2026-09-06
适用基线：第八阶段 Task 4
原则：测试夹具、Mock、合成样本和单元测试只证明代码行为门禁；真实模型、真实硬件、真实授权数据和可回溯日志才可形成生产验收结论。

## 1. 验收状态与证据要求

每个结论必须包含：代码提交、Profile、主机硬件输出、命令、输入性质、输出文件、日志时间窗和人工复核人。状态只允许 `PASS`、`FAIL`、`BLOCKED` 或有理由的 `N/A`。

- `PASS`：命令和真实证据满足本方法的门槛。
- `FAIL`：真实证据未满足门槛；不得用重跑 Mock 覆盖。
- `BLOCKED`：缺少客户硬件、授权数据、模型制品或访问条件；必须写明提供方、取证命令和不得替代的结论。
- `N/A`：该项确实不适用于被测功能，并写明理由。

H100 仅可用于本地调用链、配置门禁和功能性验证；不得把 H100 的吞吐、显存、并发、上下文或稳定性外推到双 RTX A6000。没有客户授权身份证标注集时，不计算身份证准确率。

## 2. 测试对象与数据集

| 对象 | 证据位置 | 使用方式 | 当前状态 |
|---|---|---|---|
| 知识库 60 题测试包 | `knowledge_base_package/04_test_suite/` 与 `outputs/` | 检索、引用、版本、生效日期、不可回答、安全拒答 | 有历史结果；需区分导入链路与直接索引链路 |
| 公开法规/标准文本 | `knowledge_base_package/01_official_original/`、`02_ingestion_ready/` | 来源溯源和文本索引 | 以 `SOURCE_MANIFEST.md` 复核完整性；有效性需人工复核 |
| 项目内部样本 | `knowledge_base_package/03_project_internal_samples/` | 仅测试项目规则隔离和检索行为 | README 明确为虚构样本，不是客户验收证据 |
| 本地模型性能集 | Benchmark 命令生成的 `reports/*.json` | 2K/8K/16K/24K/32K，串行/并发 | 客户 A6000 报告缺失，`BLOCKED` |
| 客户身份证标注集 | 客户授权目录（当前未提供） | 字段完整性、校验、置信度、水印和人工确认 | `BLOCKED` |

历史知识库回归报告记录：60/60 接口成功、非加权 93.33%、加权 92.34%，但也记录了导入链路未完全证明、若干答案质量问题；首轮 12 题报告记录加权 85.2%。这些是历史报告中记录的结果，不是本次重新执行的结果，也不能替代客户生产验收。

## 3. 功能与质量指标

### 3.1 知识库/RAG/问答

至少覆盖：

1. 事实命中、数值/阈值、跨文档组合、版本和生效日期。
2. 引用真实性、定位一致性、引用去重和证据充分性。
3. 无答案、空结果、条件不足、提示注入、虚构来源和敏感数据导出拒绝。
4. 项目/知识库权限隔离、停用资源拒绝、检索降级不扩大范围。
5. 导入解析成功、解析失败、索引失败、重复索引和重试后的状态一致性。

建议质量指标：

- 题目级：完全正确/部分正确/错误，另统计不可回答与安全题的错误放行数。
- 引用级：引用是否真实存在、是否支撑结论、是否存在越权来源；任何虚构引用或跨项目证据均为阻断项。
- 端到端：接口成功率、P50/P95 响应时间、失败类型、重试次数和最终状态。
- 阈值：测试包 README 给出加权得分率不低于 85% 的建议标准；正式项目验收须先确认题集、权重和人工评分人，不能把建议标准直接套作客户合同承诺。

### 3.2 本地模型性能与稳定性

在客户双 RTX A6000 主机执行。先加载被选中的 Profile，再运行 benchmark；不要依赖 benchmark 默认值：

```bash
set -a
source deploy/model-profiles/a6000x2-production-32k.env.example
set +a
./scripts/start-all.sh --model-profile "$MODEL_PROFILE_NAME"
python3 scripts/benchmark-local-models.py \
  --profile "deploy/model-profiles/${MODEL_PROFILE_NAME}.env.example" \
  --lengths 2000,8000,16000,24000,32000 \
  --concurrency 1,2 --runs 3 \
  --output reports/a6000-production-benchmark.json \
  --validated-on-host
```

每次报告必须核对并归档。`summaryByLengthAndConcurrency` 必须逐一列出每个 `length × concurrency` 组合的样本数、通过数、错误计数和三项指标的 P50/P95；`profile` 必须包含 chat model ID 和 revision：

- 每个长度与并发组合的 TTFT、总耗时、输出 tokens/s，以及 P50/P95；
- `nvidia-smi` 的设备名、总显存、已用显存、GPU 利用率采样；
- OOM、超时、连接重置/重启、排队和服务健康状态；
- Embedding 与 Reranker smoke 结果；
- 报告中的 `validatedOnHost`、Profile 名称、模型 served name 和 revision；
- 32K 失败时切换 `a6000x2-stable-16k` 的原因与重新执行结果。

没有客户 A6000 JSON 前，上述每个性能结论均为 `BLOCKED`。H100 上执行相同脚本时，输出只能归档为功能性/门禁证据，并显式写明主机不是 A6000。

### 3.3 可靠性与安全

必须验证：模型不可达、空响应、无效结构、超时、容器重启、Embedding/Reranker 单点失败、日志敏感信息、公共推理端点拒绝、跨项目资源拒绝和重复任务幂等。成功标准是明确失败状态、有限重试、可诊断日志和无敏感泄漏，不是“返回一个看起来合理的答案”。

## 4. 十九类验收矩阵

以下类别来自 Stage 8 设计基线；适用功能逐格填写结果，不能省略：

| 类别 | 核验问题 |
|---|---|
| normal | 标准输入是否完成主链路并有可追溯结果？ |
| boundary | 上下限、类型和状态边界是否按契约处理？ |
| empty result | 空结果是否明确呈现而非推断为安全/合规？ |
| partial evidence | 是否保留已有证据并标人工确认/部分成功？ |
| no evidence | 是否拒绝编造事实、引用和准确率？ |
| format variants | Office、PDF、图片、编码和结构变体是否覆盖？ |
| long input | 长输入是否受预算约束且不丢失后部关键信息？ |
| multi-turn | 同会话承接、跨会话隔离是否正确？ |
| refresh recovery | 刷新后任务、结果和已执行操作是否恢复？ |
| concurrent clicks | 重复/并发提交是否幂等或明确冲突？ |
| permission isolation | 未授权用户/跨项目 ID 是否在模型调用前拒绝？ |
| disabled resources | 停用项目、知识库、数据源、模板是否不能启动新任务？ |
| async status | 中间态、终态、部分成功、失败和重试是否一致？ |
| database failure | 连接/认证/超时是否不误修 SQL，可修 SQL 是否有限重试？ |
| model failure | 空响应、无效结构、不可达是否形成有界失败？ |
| retrieval degradation | 检索/重排降级是否保持证据和权限边界？ |
| timeout | 超时是否终止、可诊断、可安全重试？ |
| download contents | 下载是否核验权限、文件头、实际内容和错误占位？ |
| mobile layout | 移动视口的表单、状态、证据、操作和下载是否可用？ |

## 5. 评测命令与结果登记

### 5.1 静态/配置门禁

在 Linux 的 LF checkout 中执行。`model-profile-contract.tests.sh` 当前按 LF 行尾匹配 Profile 与 Compose；Windows `core.autocrlf=true` 产生 CRLF 时会形成假失败，因此 CRLF 工作树的结果标为 `BLOCKED`，不得解释为模型配置失败。应在 Linux checkout 复核，或先在临时副本运行 `dos2unix`，不得为通过测试而改写受审配置：

```bash
cd smart_worksite
bash scripts/model-profile-contract.tests.sh
bash scripts/local-inference-docs.tests.sh
bash -n scripts/check-gpu-runtime.sh scripts/check-local-models.sh scripts/start-all.sh scripts/status.sh
```

这些命令证明配置合同、脚本语法和文档合同；不证明模型已下载、硬件性能或 license 合规。

### 5.2 知识库文件完整性

`knowledge_base_package` 不属于 `smart_worksite` Git 工作树，而是独立交付制品和知识库验收前置条件。交付方必须先提供其目录、版本和 `SOURCE_MANIFEST.md`；缺失时知识库/RAG 项为 `BLOCKED`。按治理说明中的 manifest 命令校验并保存输出和时间；任何字节数或 SHA-256 不匹配均为 `FAIL`。

### 5.3 结果文件与人工复核

每次运行创建不可覆盖的带时间文件，例如：

```text
reports/<date>-<host>-<profile>-model-benchmark.json
reports/<date>-<dataset>-qa-results.json
reports/<date>-logs/<service>.log
```

人工复核至少记录：题目 ID、输入文件性质（公开/虚构/客户授权/合成）、模型 Profile、检索来源、答案结论、引用、评分、失败原因、复核人和时间。禁止把 `mock`、`stub`、合成响应或自动化 fixture 填入真实验收结果。

## 7. 取证命令（阻塞解除后）

```bash
# 模型/硬件事实
nvidia-smi --query-gpu=index,name,memory.total,driver_version --format=csv,noheader
docker compose -f deploy/docker-compose-env.yml -f deploy/docker-compose-models.yml \
  --env-file deploy/.env \
  --env-file "deploy/model-profiles/${MODEL_PROFILE_NAME}.env.example" ps
docker compose -f deploy/docker-compose-env.yml -f deploy/docker-compose-models.yml \
  --env-file deploy/.env \
  --env-file "deploy/model-profiles/${MODEL_PROFILE_NAME}.env.example" \
  logs --tail=200 local-llm local-embedding local-reranker

# 供应链事实（下载后保存响应和人工复核记录）
for model in Qwen/Qwen3.8-27B-FP8 Qwen/Qwen3.8-27B Qwen/Qwen3-Embedding-4B Qwen/Qwen3-Reranker-0.6B; do
  curl -fsSL "${HF_ENDPOINT:-https://huggingface.co}/api/models/$model" \
    -o "reports/${model##*/}-metadata.json"
done

# 文档链接/命令及工作树门禁
bash scripts/local-inference-docs.tests.sh
git diff --check
```

取证完成后，必须把原始输出、时间、主机和人工复核记录加入验收报告；不能仅把命令写进文档就把状态改为 `PASS`。
