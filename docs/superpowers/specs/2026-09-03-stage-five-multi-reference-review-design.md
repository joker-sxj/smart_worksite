# 阶段五：多资料长文档合规审查设计

## 目标

在现有“主审查文件 + 审查模板 + 本地模型”基础上，支持一个主审查文件关联多个参考资料，并对长文档按审查规则动态检索、分段审查、保存可追溯证据，形成可恢复的生产闭环。

## 范围

- 主审查文件：一次一个，支持当前已支持的 Word/PDF 审查文件。
- 审查模板：支持已解析的 Word/PDF/Excel/CSV 模板，解析失败时禁止启动审查。
- 参考资料：支持当前项目已授权、解析成功且可检索的知识库文档；支持本次上传的临时 PDF/Word 参考文件。
- 每条规则单独检索主文件和参考资料，最多一次补检。
- 结果包含规则状态、问题、建议、严重程度、置信度、主文件证据和参考依据。
- 全部推理使用本地模型；禁止 Mock 结果作为实机验收证据。

不包含：报告图表、自定义审查字段、身份证水印增强、跨项目权限模型重构和模型训练治理文档。

## 方案

采用“规则拆解 + 分层检索 + 分规则审查”。Java 负责权限、文件关系、任务状态和结果持久化；复用现有解析、切片、动态检索和本地 AI 网关；Python 只接收当前规则所需的有界主文件证据和参考依据，并返回严格 JSON。程序负责来源归属、定位、字段校验和汇总统计，模型不负责页码、计数或权限判断。

## 数据和接口

增加审查参考资料关系和规则结果持久化，保留现有 `issuesJson`/`resultJson` 兼容历史记录。提交请求增加可选 `referenceDocumentIds` 与 `referenceFileIds`；所有 ID 在服务端按当前项目重新授权校验。规则结果保存主文件证据、参考证据、置信度、人工确认标记和错误原因。

总体状态为 `PENDING -> PARSING -> RULES_READY -> REVIEWING -> COMPLETED/PARTIAL_SUCCESS/FAILED`；规则状态为 `PENDING -> RETRIEVING -> AI_REVIEWING -> COMPLETED/NEEDS_MANUAL_CONFIRMATION/FAILED`。解析失败、权限失败和无可用证据必须有可操作错误；规则失败不丢失其他规则结果，也不触发无限重试。

## 前端交互

合规审查页保留主文件和模板选择，新增参考资料多选区：显示当前项目可用文档的解析/入库状态、文件类型和定位信息，支持临时参考文件多选、删除和提交前校验。提交后展示解析、规则准备、检索和审查进度；结果按规则展示主文件问题与参考依据，缺证据项标记人工确认。刷新后从服务端恢复任务和结果，不使用本地临时状态覆盖最终状态。

## 错误和安全

参考资料必须属于当前项目，必须是解析成功且未删除的文档；临时文件沿用项目文件权限。不得把参考资料内容误标为主文件问题，不得泄露对象存储地址、堆栈、密码、Token 或完整敏感正文。补检最多一次，相同失败不重复执行；模型返回空 JSON、非法 JSON、缺少证据归属或越权来源时，规则进入失败/人工确认而非伪造成功。

## 验收

自动化测试覆盖多参考资料关系、项目隔离、模板/主文件/参考文件解析失败、长文本分段、规则级部分成功、补检上限、证据归属和历史兼容。Linux 使用真实本地模型和真实文件部署，Chrome 至少 40 个不重复场景，覆盖零/一/多参考资料、PDF/Word、跨页定位、无证据、部分证据、刷新、重试、越权、模型异常和并发提交。验收后检查 Java、Python、本地模型、Embedding、Reranker、MySQL、Redis、MinIO、前端和容器日志，修复新异常后再推送 `joker-sxj/main`。
